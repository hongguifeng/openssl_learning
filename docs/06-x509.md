# 第 6 章：X.509——证书验证不是“读出 subject”

证书是一个由 CA 签名的结构，包含公钥、主体信息、有效期、用途扩展和签名。验证证书时，必须把数学签名验证、信任根、链构建和业务名称/用途策略放在一起看。

## 6.1 证书链的结构

```text
Root CA（信任锚，设备预置）
   └─ Intermediate CA（可轮换）
       └─ Server/Device certificate（端实体）
```

设备通常不应该把任意服务器证书直接写进代码；更常见的是预置一个或多个信任根，服务器发送自己的证书和中间证书，客户端构建链并验证每个签名。

## 6.2 `X509_STORE` 和 `X509_STORE_CTX`

- `X509_STORE` 是可复用的信任库和验证参数容器；
- `X509_STORE_CTX` 是一次具体验证的临时上下文；
- `X509_verify_cert` 执行链构建和验证；
- `X509_STORE_CTX_get_error` 提供失败分类，如过期、找不到颁发者、名称不匹配。

不要把一次验证的 `X509_STORE_CTX` 跨线程复用。`X509_STORE` 的共享策略也要结合证书更新和锁设计。

## 6.3 验证至少包含哪些条件

1. 证书签名链能追溯到信任根；
2. 当前时间在 `notBefore/notAfter` 范围内；
3. 主机名匹配 `subjectAltName`；
4. `KeyUsage`/`ExtendedKeyUsage` 允许当前角色；
5. 算法和密钥强度满足安全级别；
6. 产品需要时检查吊销状态（CRL/OCSP 或专用设备策略）。

只调用 `PEM_read_X509` 只能证明文件格式可解析，不能证明对端可信。

## 6.4 主机名为什么要单独设置

证书中的 CN 是历史兼容字段，现代验证应通过 `X509_VERIFY_PARAM_set1_host` 设置期望主机名。验证库会根据 SAN 中的 DNS/IP 条目匹配；如果主机名错误，数学签名仍然正确，但身份验证必须失败。

## 6.5 实验：成功和失败都要运行

```sh
cmake --build build --target openssl_x509_verify
ctest --test-dir build -R x509_verify --output-on-failure
```

脚本会生成带 `DNS:localhost` 的自签名证书，把它作为实验信任根，然后执行：

- `localhost`：应成功；
- `wrong.example`：应失败。

这两个结果一起出现，才能证明代码确实检查了主机名，而不是“只要证书能读就通过”。

## 6.6 与 TLS 的关系

X.509 验证可以单独调用，也可以配置到 `SSL_CTX`。TLS 客户端通常需要同时完成：

```text
SSL_CTX_load_verify_locations       → 信任根
SSL_CTX_set_verify                  → 验证模式
X509_VERIFY_PARAM_set1_host         → 主机名
SSL_connect                         → 握手期间触发验证
```

生产代码还要检查 `SSL_get_verify_result` 或握手返回值，并记录可诊断但不泄露密钥的错误原因。

## 6.7 学习检查点

1. Root CA 为什么被称为 trust anchor，而不是“链中普通证书”？
2. 证书签名正确但 SAN 错误时，应该通过还是失败？
3. `X509_STORE` 和一次验证的 `X509_STORE_CTX` 为什么要分开？
